# v0.4.0 技術設計：本機 DNS 過濾引擎與三段攔截強度

狀態：設計（實作前）
範圍：**只在開發分支進行**。本輪不 push、不 tag、不發布、不升版。

---

## 1. 目的

在既有「DNS-only VPN + 上游 DoH（AdGuard Home）」架構上，加入**在本機執行的網域規則過濾**：
裝置在把查詢送出上游之前，先用本機快照比對，命中即直接回覆封鎖結果，未命中才走既有 DoH。

使用者可見的結果：三段強度（寬鬆／標準／嚴格）、訂閱來源管理、自訂訂閱、手動允許／封鎖，
以及**每個模式實際生效狀態的可驗證顯示**。

---

## 2. 現況（v0.3.0）與真正能攔截的範圍

已由程式碼確認：

- VPN 只宣告 `10.111.222.1/32`、虛擬 DNS `10.111.222.2`、唯一一條 `10.111.222.2/32` 路由
  （`VpnRoutePlanPolicy` 拒絕 catch-all 與非 /32 的 DNS 路由）。非 DNS 流量完全不進 VPN。
- 只處理 **IPv4 / UDP** DNS。送往虛擬 DNS 的 TCP 查詢會進隧道但被丟棄（回 TC=1 讓用戶端重試失敗）。
- 查詢流程：reader thread 讀 TUN → `DnsTunnelPacket` 判定 `Query` 或 `Drop(reason)` →
  `dispatch()`（`DnsStatsRepository.recordQuery()` 後丟進有界執行緒池）→ `handleQuery()` 走 DoH →
  驗證回應後重建 IPv4+UDP 寫回 TUN。
- DNS 解碼／編碼：`DnsMessageReader.readQuery()` 產生 `ParsedDnsQuery(header, question,
  questionEndOffset, ednsUdpPayloadSize)`；`DnsMessageWriter.responseHeaderOnly(queryBytes,
  queryLength, rcode, truncated)` 會**沿用查詢的 ID 與 Question 區段**並套用指定 RCODE。
  → **封鎖回覆不需要新的 DNS 編碼器**，直接重用 `responseHeaderOnly(..., NXDOMAIN, false)`。
- 網路切換：`UnderlyingNetworkPolicy` + tunnel generation guard 讓底層網路跟隨系統預設網路；
  只有真正改變時才重建 DoH 傳輸。

### 三種 Android 私人 DNS 模式的實際資料流

| 模式 | 虛擬 DNS 宣告 | 查詢是否經過本機隧道 | 本機過濾是否可能生效 |
| --- | --- | --- | --- |
| OFF | 是 | **是**（系統 resolver 會用我們的虛擬 DNS） | **可以** |
| OPPORTUNISTIC（自動） | 是 | **是**（同上；系統只有在既有 DoT 失敗時才退回） | **可以**，但需在實機確認 |
| HOSTNAME（strict 指定主機名稱） | **否**（E2） | **否**：系統自行對指定主機做 DoT，完全不使用虛擬 DNS | **不可能** |

E2 的決策點只有一處：`DnsExperiment.effectiveMode` 在 strict hostname 時回傳
`E2_NO_DNS_DECLARATION`（隧道照樣建立、但**不** `addDnsServer`）。本輪**不得改動這個行為**。

## 3. 架構阻擋評估

結論：**沒有阻擋**，但有一個必須誠實呈現的物理限制。

- M1／M2 是純 Kotlin 葉模組，不依賴 Activity／Compose／Android framework，可完整單元測試。
- M3 的插入點在既有的 `handleQuery()` 之前，屬純 CPU 判斷；封鎖回覆重用既有 writer，
  不新增 socket 處理，也不改變非 DNS 封包的既有政策。
- **stric 私人 DNS 下本機過濾在物理上不可能生效**（系統根本不把查詢交給我們）。因此該模式下
  本機強度必須顯示為「暫不生效」，且不得宣稱過濾成果。這是政策，不是缺陷。

## 4. M1：規則引擎

模組（`tw.kuies.block.filter`，全部為純 Kotlin）：

| 型別 | 職責 |
| --- | --- |
| `FilterProfile` | RELAXED／STANDARD／STRICT，各對應一份主清單定義（不疊加） |
| `FilterSubscription` | 一個訂閱來源：id、顯示名稱、url、是否內建、是否啟用、狀態（未就緒／已就緒／失敗）、上次成功時間、規則數、錯誤摘要 |
| `DnsRuleParser` | 文字 → `ParsedRules`（規則集合 + 統計：接受數、跳過數、拒絕原因計數） |
| `DnsRuleEngine` | 不可變快照的查詢介面：`decide(domain): FilterDecision` |
| `FilterSnapshot` | 不可變資料：4 組來源 × 2 種匹配範圍的已排序網域陣列 + 版本與統計 |
| `FilterRepository` | 組裝快照（讀取訂閱內容 → 解析 → 產生快照），並保留「最後可用快照」 |

### 4.1 支援的規則語法（第一版）

| 形式 | 語意 |
| --- | --- |
| `||domain^` | domain 與其所有子網域（SUBDOMAIN） |
| `@@||domain^` | 允許例外（同上範圍） |
| 純網域（`domain.tld`） | domain 與其所有子網域 |
| hosts 封鎖（`0.0.0.0 domain.tld` / `127.0.0.1 domain.tld`） | domain 與其所有子網域 |
| `!` 開頭、`[Adblock Plus]` 等 `[...]` 標頭 | 註解，計入註解數 |
| 空白行 | 略過 |

**明確拒絕並計數（絕不當成一般網域規則）**：任何帶 Adblock modifier（`$`）、regex（`/.../`）、
萬用字元（`*`）、CSS 選擇器（`#`）、`#@#`、DNS rewrite、`@@` 的萬用字元例外、以及無法轉為合法
網域的字串。拒絕原因分桶統計（`MODIFIER`、`REGEX`、`WILDCARD`、`CSS`、`INVALID_DOMAIN`、
`TOO_LONG`），供 UI 顯示與測試斷言。

### 4.2 匹配語意（完全匹配 vs 子網域）

- `MatchScope.EXACT`：只有查詢網域與規則字串**完全相同**才算命中。
- `MatchScope.SUBDOMAIN`：查詢網域等於規則，或是規則加上至少一個標籤的後綴（`a.example.com`
  命中 `example.com`；`notexample.com` **不**命中 `example.com`）。
- 檔案格式（`||domain^`／純網域／hosts）一律產生 `SUBDOMAIN`；只有**使用者手動**允許／封鎖
  項目可選 `EXACT`（預設 `SUBDOMAIN`）。
- 邊界：忽略大小寫；去尾點；IDN 以 `java.net.IDN.toASCII` 正規化（失敗即拒絕）；單一標籤
  （如 `localhost`）可作為網域但長度上限 253／標籤 63，超長即拒絕。

### 4.3 優先順序

依序判定，第一個命中即決定：

1. 使用者手動**允許** → ALLOW
2. 使用者手動**封鎖** → BLOCK
3. 訂閱中的**允許例外**（`@@`） → ALLOW
4. 訂閱中的**封鎖** → BLOCK
5. 無命中 → **UPSTREAM**（交給既有 DoH，不影響既有行為）

每一層都先比 `EXACT` 再比 `SUBDOMAIN`（同層內精確者優先）。手動允許只代表「本機不封鎖」，
**不代表上游 AdGuard Home 一定允許**——UI 文案必須這樣寫。

### 4.4 成本模型（可預測）

- 快照為**不可變**結構，讀取端零鎖。
- 每組為已排序的 `Array<String>`（小寫、去尾點），以 `binarySearch` 查詢；
  一次查詢的成本 = 標籤數（≤ 8）× 組數（4）× O(log n)，**不隨規則數線性走訪**。
- 記憶體 ≈ 規則字串總量；以 HaGeZi `multi`（161,902 條）估算為數 MB 等級，實測值列入報告。
- 快照建置（解析 + 排序 + 去重）在背景執行，不在 VPN 封包路徑上。

### 5.2 下載安全要求（實作必守）

- 僅 `https`；由既有 OkHttp 憑證驗證處理（**不得**關閉 TLS 驗證、不得信任所有憑證）。
- 主機白名單：內建來源僅允許其官方主機；**自訂來源**禁止 `http`、禁止指向本機／私有位址
  （`127.0.0.0/8`、`10/8`、`172.16/12`、`192.168/16`、`169.254/16`、`::1`、link-local、`.local`，
  以及解析後落入上述範圍者）→ 防 SSRF。
- 重新導向上限（≤ 3）且每一跳都重新檢查主機與位址。
- 下載大小上限 16 MB（實測最大 4.7 MB），並在串流過程中即時中止超限。
- 解析上限：規則數上限 500,000、單行長度上限 4,096、總解析時間上限（逾時即放棄該次更新）。
- **不執行**任何遠端指令：清單只被當成文字解析，永不執行、不載入程式碼、不遞迴抓取清單中的其他 URL。
- **原子更新**：先寫入暫存檔，解析成功且通過上限檢查後才整批取代；任何失敗**保留上一份有效快照**。
- 併發：每個訂閱同時只有一次更新在跑（mutex／in-flight 標記），重複觸發直接略過。

### 5.3 持久化

- 內容存於 `filesDir/filters/<subscriptionId>.list`（暫存檔 `.tmp`）。
- 狀態存於 `SharedPreferences`（與既有 `AppSettingsStore`／`DnsConfigStore` 相同的風格），
  鍵包含：訂閱清單 JSON、強度、上次成功時間、規則數、錯誤摘要。**不儲存使用者查詢紀錄**。
- 初次安裝即沒有可用清單 → UI 顯示「本機規則尚未就緒」，且不得宣稱過濾生效。

## 6. M3：與 VPN 流程整合

- 插入點：`handleQuery()` 取得解析後查詢後、呼叫 DoH 之前。**只在查詢確實經過本機隧道時**才適用
  （即 `DnsExperiment.effectiveMode == BASELINE` 才有虛擬 DNS 宣告）。
- 流程：正規化網域 → `FilterSnapshot.decide()` →
  - BLOCK：以 `DnsMessageWriter.responseHeaderOnly(bytes, length, NXDOMAIN, false)` 產生回覆，
    重用既有寫回路徑（保留 Transaction ID 與 Question），**不發出任何上游請求**。
  - ALLOW／UPSTREAM：沿用既有 DoH 路徑，行為不變。
- 不把規則清單傳給 AdGuard Home；不持久化使用者查詢紀錄（只保留既有每日彙總計數）。
- 生命週期：快照以 `volatile` 參照發布，更新即整批替換（讀者不需鎖）；服務停止或底層網路重建時
  不得殘留舊快照造成誤判；私人 DNS 模式變更時即時重新評估「本機過濾是否生效」。
- 封鎖回覆類型：**NXDOMAIN**（與既有上游封鎖語意一致，且已被現有統計視為 blocked）。
  A／AAAA／其他 QTYPE、EDNS、壓縮名稱、畸形查詢與大小上限皆有單元測試。
- 既有非 DNS 封包政策、TCP 查詢丟棄行為、`VpnRoutePlan`、`UnderlyingNetworkPolicy`、
  **E2 strict 行為全部不改**。

## 10. 實測補充（2026-10-15，SM-F7660）

### 10.1 strict 模式仍然保留 /32 路由（容易被誤判成 bug）

`DnsExperimentPlanner.declarationFor` 在 `E2_NO_DNS_DECLARATION` 只把 `dnsServer` 設為 null，
**`dnsRoute` 仍在**；`establishTunnel` 因此照樣 `addRoute(10.111.222.2/32)`。實機 dump 可見：

```
LinkAddresses: [ 10.111.222.1/32 ]  DnsAddresses: [ ]
Routes: [ 10.111.222.2/32 -> 0.0.0.0 tun0, ::/0 unreachable, 10.111.222.1/32 -> 0.0.0.0 tun0 ]
```

**這不是本輪造成的，也不是缺陷**：E2 的意義是「不宣告自己為 resolver」，而路由保留代表
「有人明確把封包送來虛擬 DNS 時，隧道照樣回答」。在 v0.3.0 這些封包會走 DoH；本輪之後，
命中本機規則的會被本機以 NXDOMAIN 回答，未命中的仍走 DoH（已實測）。

對使用者的實際影響：strict 模式下**系統 resolver 不使用虛擬 DNS**，所以系統層級的本機過濾
不生效（`LocalFilterPolicy` 回報 `PAUSED_PRIVATE_DNS`），但「明確送往 10.111.222.2」的查詢
仍會被本機規則正確處理。任何測試都不得用後者來宣稱前者生效。

### 10.2 真機驗證結果

`scripts\device-test.ps1 -Scenario filter -AllowDeviceChanges -StopOtherVpn`
在 strict(hostname) 與 opportunistic 兩種私人 DNS 模式下各 **9/9 PASS**：
E2 宣告契約、本機規則命中（NXDOMAIN + answers=0 + 本機封鎖計數 +1）、未命中仍走上游、
未命中不增加本機計數、清空規則後恢復解析、AdGuard 還原。

回歸：`protection` 10/10 PASS、`dns-declaration` 12/12 PASS。
