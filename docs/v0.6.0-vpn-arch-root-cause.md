## 1. 問題 A：無線偵錯顯示 VPN 位址

### 1.1 顯示值從哪裡來 [碼]

AOSP `packages/apps/Settings` 的無線偵錯頁面由
`AdbIpAddressPreferenceController.getIpv4Address()` 決定，實作是：

```java
private static String getDefaultIpAddresses(ConnectivityManager cm) {
    LinkProperties prop = cm.getLinkProperties(cm.getActiveNetwork());
    return formatIpAddresses(prop);
}
```

`formatIpAddresses` 取 `LinkProperties.getAllLinkAddresses()` 的**第一個 IPv4**。
沒有其他來源、沒有過濾 VPN、沒有偏好 Wi-Fi。

因此只要「繪製該頁面的程序」其 `getActiveNetwork()` 是 VPN，畫面就會顯示
VPN 介面位址（本專案為 `10.111.222.1`），與 Wi-Fi 完全無關。這正是回報的
`10.111.222.X`。

### 1.2 為什麼 AdGuard 沒這個問題 [機]

同一台裝置（SM-F7660，Android 16）`dumpsys connectivity`：

| 項目 | AdGuard（現行） | KuiesBlock（設計） |
| --- | --- | --- |
| `com.android.settings` UID | `1000`（與 `9501000`） | 同 |
| VPN `Uids:` 集合 | `{0-999, 1002-5008, …}` → **排除 1000、1001** | 未排除任何系統 UID → 涵蓋 1000 |
| VPN `LinkAddresses` | `172.18.11.218/32`（＋IPv6） | `10.111.222.1/32` |

`com.android.settings` 以 system UID `1000` 執行；AdGuard 的 VPN 恰好不涵蓋
UID 1000，所以 Settings 的 `getActiveNetwork()` 仍是有線／Wi-Fi 網路，頁面
自然顯示實體位址。KuiesBlock 目前涵蓋 UID 1000，Settings 的預設網路就是
VPN，於是顯示 `10.111.222.1`。

### 1.3 根因

**不是**虛擬位址選得不好，也**不是**路由表問題：

> 無線偵錯的顯示值是「Settings 程序自己看到的預設網路」的第一個 IPv4；
> KuiesBlock 讓 VPN 成為 system UID 的預設網路，於是顯示 VPN 位址。

把 `10.111.222.1` 換成別的位址只會改變顯示的數字，不會改變「顯示 VPN 位址」
這件事，因此不列入方案。

### 1.4 修正方向（待實機驗證）

在建立隧道時固定排除系統 UID（等價於 `addDisallowedApplication` 一個 UID 1000
的套件），使系統元件（Settings、system_server）維持直接使用實體網路：

- 預期結果：無線偵錯頁面顯示 Wi-Fi IPv4（`192.168.31.X`），ADB 配對／連線照舊。
- 代價：**system UID 的 DNS 不再經過本機過濾器**（一般使用者 App 不受影響）。
  AdGuard 實測也是這個取捨（它同時排除了 UID 1001）。
- 需量測：排除後 `Uids:` 集合、頁面顯示值、VPN 對一般 App 的過濾是否仍有效。

## 2. 問題 B：私人 DNS「無法連線」

### 2.1 平台機制 [碼]

- strict（指定主機名稱）模式：`DnsManager` 只撥 DoT 到**該主機解析出的 IP**
  （`privateDnsCfg.ips`），且會先用 `LinkProperties` 判斷是否可達
  （`getReachableAddressList(..., lp)`）；可達清單為空就沒有任何已驗證伺服器，
  strict 模式沒有明文回退。
- automatic（自動）模式：先對「該網路宣告的 DNS」試 DoT，失敗才回退 UDP/53。
- VPN 網路同樣會被套上私人 DNS 設定：AdGuard 的 VPN `LinkProperties` 就印出
  `UsePrivateDns: true`、`PrivateDnsServerName: <使用者主機>`、
  `ValidatedPrivateDnsAddresses: [<DoT 伺服器>]` [機]。

### 2.2 兩者的差異 [機]

| 項目 | AdGuard VPN | KuiesBlock VPN |
| --- | --- | --- |
| 路由 | 幾乎全覆蓋（大量分段路由＋`0.0.0.0/0` 等價效果）、含 `198.18.53.53/32` | 只有 `10.111.222.2/32`（BASELINE）或完全沒有 DNS 路由（E2） |
| 宣告 DNS | `198.18.53.53` | `10.111.222.2` 或**不宣告**（E2） |
| DoT 封包去處 | 進 tun，由 AdGuard 的使用者空間轉送（含 TCP） | 進 tun 後被丟棄（BASELINE），或根本沒有可達路徑（E2） |
| VPN 網路私人 DNS 驗證 | **成功** | 失敗 |

BASELINE 下已直接取證：strict 模式的 DoT 撥號以
`src=10.111.222.1 dst=10.111.222.2 dstPort=853 flags=SYN` 進入 tunnel 後被丟棄
（`reason=NOT_UDP`）—— 這是 2026-10-16 的封包位址直讀結果。

### 2.3 根因

> strict 模式的 DoT 一定撥向「解析出的私人 DNS IP」。KuiesBlock 的 tun 只覆蓋
> 虛擬 DNS 位址（或什麼都不覆蓋），VPN 網路因此**沒有可達的 DoT 路徑**，
> 該網路永遠無法完成私人 DNS 驗證；而 VPN 又是 App 的預設網路，於是系統
> 判定「私人 DNS 無法連線」。

E2（不宣告 DNS）之所以「看起來可用」，是因為它讓系統改走底層網路；但先前
「E2 已驗證」的紀錄是沿 `UnderlyingNetworks` 判讀**底層電信網路**的私人 DNS，
不是 VPN 網路本身（harness 的既有規則就是只看實際承載網際網路的底層網路）。
這是量測盲點，不是 E2 真的讓 VPN 網路通過驗證。

### 2.4 候選方案比較

| 方案 | 做法 | 成本 | 能同時達成 B 嗎 | 限制 |
| --- | --- | --- | --- | --- |
| B1 宣告真實 DoT 位址（E1 式） | strict 時 `addDnsServer(<解析出的 DoT IP>)`、不加該 IP 的路由；VPN 網路因此「可達」，封包走底層網路 | 小（沿用現有 E1 原型與 bootstrap） | 待驗 | strict 下本機過濾本來就不生效，需如實標示 |
| B2 全流量 VPN＋TCP 轉送 | 複製 AdGuard 做法：全路由＋使用者空間 TCP/ UDP 轉送 | 大（TCP 狀態機 1.3k–2k 行，或引入原生 netstack，違反限制） | 是 | 風險與維護成本高，且 strict 下仍無法過濾（TLS 端到端） |
| B3 維持 E2＋標示限制 | 不改行為，只把「无法攔截」說清楚 | 零 | 否 | 不符合本次驗收 |

B1 的關鍵未知：strict 模式下 VPN 網路把 DoT 撥向「已宣告的 DNS 位址」時，
封包是否如一般未覆蓋流量一樣落到實體網路。AdGuard 的 `192.168.31.1/32`、
區網未覆蓋仍可通行，支持「未覆蓋即落到實體網路」[推]。B1 曾在 2026-10-12
被量測為未驗證，但那次沒有讀 VPN 網路自身的 `ValidatedPrivateDnsAddresses`，
且量測視窗可能不足 [推]。**必須重測才能定案。**

前提：測試機目前 Wi-Fi 關閉、AdGuard 佔用 VPN、私人 DNS 為 strict。

| R5 | 讀 VPN 網路 `LinkProperties`（含 `UsePrivateDns`／`ValidatedPrivateDnsAddresses`）、無線偵錯頁顯示值、App 內解析探測 | 判定 A、B 的真實現況 | 無 |
| R6 | 以 debug broadcast 切 E1，重啟隧道，重讀同一組 | 驗證 B1 是否成立 | 切回預設 |

判定紀律：A／B 各自以 **PASS／FAIL／INCONCLUSIVE** 記錄；不以單元測試替代；
不以狀態列圖示判定；私人 DNS 需同時看 VPN 網路與底層網路，並以 App 內解析
探測證明一般 App 真的能解析。

## 4. 實機結果（2026-10-30，SM-F7660 / Android 16）

### 4.1 三種宣告在 **VPN 網路本身** 的私人 DNS 狀態 [機]

`dns-declaration` 情境（12/12 PASS）保存的 `dumpsys connectivity`：

| 模式 | VPN 網路 `DnsAddresses` | VPN 網路私人 DNS | VALIDATED |
| --- | --- | --- | --- |
| `e2`（出貨於 strict） | 空 | 無 `PrivateDnsBroken` | **是** |
| `e1` | 真實 DoT 位址 | **`PrivateDnsBroken`**、無 `UsePrivateDns` | 否 |
| `baseline` | 虛擬 DNS | 無 `PrivateDnsBroken` | 否 |

**結論：B1（宣告真實 DoT 位址）不成立。** 只把位址宣告成 DNS 不會讓 VPN 網路
可達 DoT，平台直接把它標成 `PrivateDnsBroken`。B2（全流量＋TCP 轉送）成本過高
且 strict 下仍無法過濾；B3 不符合驗收。因此**維持 E2**，並改由「系統 UID 不進
隧道」讓私人 DNS 頁面回到它真正該看的那個網路。

### 4.2 修正後（worktree 建置）

| 檢查 | 結果 | 證據 |
| --- | --- | --- |
| VPN `Uids` 是否排除系統 UID | **PASS** | `Uids: <{0-999, 1001-99999}>`（修正前為 `{0-99999, …}`） |
| 無線偵錯頁面顯示值 | **PASS** | 隧道啟動中仍顯示 `192.168.1.135:<port>`（Wi-Fi 實體 IP） |
| ADB 以顯示值連線 | **PASS** | `adb connect 192.168.1.135:<port>` → `device` |
| strict 私人 DNS 下 App 內解析 | **PASS** | `RESOLVE_SYSTEM`：`probe-*.github.io` OK（4 個位址）、`example.com` OK（2 個） |
| Wi-Fi 網路私人 DNS 驗證 | **PASS** | `UsePrivateDns: true`、`ValidatedPrivateDnsAddresses` 存在（隧道啟動中） |
| 本機過濾未退化 | **PASS** | 種入 1 條規則後 App 內探測 `rcode=NXDOMAIN answers=0 locallyBlocked=1` |
| protection 情境（啟停、VALIDATED、E2 契約） | **PASS** | 10/10 |
| Wi-Fi 重新連線後保持 | **未測** | 本回合未做中途切換，維持既有已驗收結論 |

限制（必須如實呈現）：strict 模式下本機規則不參與解析，查詢計數維持
「無資料」；VPN 網路本身仍不會有私人 DNS 驗證狀態，這是 DNS-only 架構的
平台事實，不是被掩蓋的錯誤。

### 4.3 證據等級說明

「修正前頁面會顯示 `10.111.222.1`」是 [碼]（AOSP 取用 `getActiveNetwork()`）
＋ [機]（修正前 `Uids` 涵蓋 1000）的推論，該回合未在未修正的建置上實際截圖；
修正後則是實機頁面直讀。AdGuard 對照同理：差異由 `Uids` 集合直接證明。
