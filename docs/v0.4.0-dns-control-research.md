## 2. 實際 DNS 架構（程式碼 + 本輪實機量測）

模式只由一個地方決定：`KuiesVpnService.startProtection()` 讀取設定後（`KuiesVpnService.kt:269-271`）呼叫 `DnsExperiment.effectiveMode`，規則就是 `strictPrivateDns ? E2_NO_DNS_DECLARATION : BASELINE`（`vpn/DnsExperiment.kt:138-146`）。

| 私人 DNS | tunnel 宣告的 DNS | tunnel 路由 | 系統解析器查詢是否進本機 | 誰真的在過濾 |
| --- | --- | --- | --- | --- |
| `off` | `/10.111.222.2` | `10.111.222.2/32`、`10.111.222.1/32`、`::/0 unreachable` | **是**（本機封鎖計數 +1） | 本機規則 → 上游 AdGuard Home |
| `opportunistic`（AUTO） | `/10.111.222.2` | 同上 | **是**（本次量測） | 同上 |
| `hostname`（strict） | **無**（E2，`addDnsServer` 被跳過） | 同上（`/32` 仍在但失效） | **否**（走系統 DoT） | **只有上游 AdGuard Home** |

目前狀態不是猜的：`activeDnsPath` 由宣告推導（`KuiesVpnService.kt:354-357`），strict 下即為 `DnsPath.SYSTEM_PRIVATE_DNS`（`core/DnsPath.kt:15-21`）。

限制（程式碼）：

- 只處理 **IPv4 / UDP / 53**。`KuiesVpnService.kt:84`「Scope: IPv4 UDP DNS only. DNS-over-TCP and IPv6 DNS are not intercepted in this version」；`dns/packet/DnsTunnelPacket.kt:46` 對非 UDP 直接「TCP DNS is intentionally not proxied in this version」。
- 只有 `/32` host route，**沒有預設路由**（`VpnRoutePlan.kt`，由 `VpnRoutePlanPolicy` 強制）——這正是「不會切斷使用者網路」的原因，也是它永遠不可能攔到 DoT 的原因。
- **TCP/53 送往 `10.111.222.2` 的封包會被收進 tunnel 然後被默默丟掉**：沒有回應、不送 RST（`readLoop` 只寫 log，`KuiesVpnService.kt:616-627`），客戶端只能等自己逾時。
- 回應超過 UDP 預算時只回截斷的 NOERROR（`KuiesVpnService.kt:711-720`），**沒有 TCP 重試路徑**。
- `allowFamily(AF_INET)` 使 tunnel 網路帶 `::/0 unreachable`（實機 dump 可見）。App 的 IPv6 是否因此受影響，本輪**未量測**。

平台面的推論（程式碼本身只把它當假設）：BASELINE 下 Android 解析器確實會使用我們宣告的虛擬 DNS；strict 下解析器改對私人 DNS 主機解析出的位址開 DoT/853，而該位址不在 `/32` 內，所以沒有任何路由會把封包交給 tunnel。

## 3. strict Private DNS 能否安全取得 DNS 控制權

**結論：不能。** 在不破壞 TLS 保護的前提下，KuiesBlock 無法取得 strict 模式下的查詢內容，也無法讓本機規則生效。

原因（AOSP `DnsManager.java`）：`tlsServers = strictMode ? getReachableAddressList(privateDnsCfg.ips, lp) : useTls ? paramsParcel.servers : new String[0]`、`tlsName = strictMode ? privateDnsCfg.hostname : ""`。strict 的目標是**設定主機名稱解析出的位址**（本次量測 `219.85.145.190`，經 `isReachable` 過濾），**不是**網路的 DHCP DNS、也**不是** VPN 宣告的伺服器；而且 strict **沒有明文 fallback**（只有 `tlsServers` 一份清單；連不上時 Android 把該網路標成「沒有網際網路」，Android P 官方部落格明文如此）。

已評估並排除的作法：

| 作法 | 結果 |
| --- | --- |
| 宣告虛擬 DNS（baseline） | 解析器改對 `10.111.222.2:853` 開 DoT，無可用憑證 → strict 下整個 DNS 不通（2026-10-11 實機） |
| 宣告真實 DoT 位址但不給路由（E1） | 實機**未通過驗證**（tunnel 不 VALIDATED） |
| 把 DoT 位址導進 tunnel | 需要一張對自架 DoH 主機名稱有效、且受**系統**憑證庫信任的憑證；使用者安裝的 CA 不適用，AdGuard 官方也說非 root 只能裝到 user store、其解法是 Magisk 模組（＝root） |
| TCP/853 逐位元轉送 | 需自製使用者空間 TCP 狀態機（約 1.3k–2k 行），且**不會恢復任何過濾**（TLS 仍端到端：NetGuard FAQ 64 也是同一句）；`protect()` 只保護自己建立的 socket，port 853 對 App 是特許埠，也沒有埠轉向 API |
| 關閉憑證驗證／偽造 DoT／靜默降級明文／封鎖 853 | 本輪明文禁止，且都破壞安全性 |
| Root 安裝自簽 CA | 非 root 不可能，且不符「不 Root」定位 |

剩下唯一的兩條路：**維持 E2**（本機不攔截，交給上游 AdGuard Home），或**引導使用者把私人 DNS 改成「自動」或「關閉」**（會降低系統層級的 DoT 加密保護，需使用者自己決定）。

## 4. AdGuard 的做法與技術差異

- AdGuard（Local VPN，非 root）**同樣受限於系統解析器這一層**：其官方 KB 明說「In VPN routing mode, apps are excluded from the local VPN by system means… **However, DNS requests come from the system resolver, not the application.** In Automatic proxy mode, it is only possible to exclude traffic from applications, not their DNS queries, because AdGuard sees them as system queries.」——與 KuiesBlock 的處境相同。
- **修正題目前提**：查證 AdGuard Settings 與 Low-level settings 兩份 KB 全文後，**找不到任何名叫 `$network`／「network compatibility」的選項（UNVERIFIED）**。`$network` 是**規則修飾詞**，只比對 IP、不能比對網域，只能搭配 `$app`／`$important`；其風險是 allowlist 形式會讓該端點**完全不再被過濾**（官方原文：「there will be no further filtering at all」）。
- AdGuard 真正改變「它看到什麼」的是 low-level 設定：**Excluded apps**（以 UID／套件排除）、IPv4/IPv6 ranges excluded from filtering、IPv6 filtering、Port ranges。
- **差異**：KuiesBlock 不終結 TLS、不裝 CA、不做憑證攔截。AdGuard 在非 root 下多做到的，主要是更完整的 App 流量處理、訂閱規則引擎與介面，**不是**看見 DoT 內容。
- **共同的天花板**：非 root、不解密 TLS 的前提下，strict 模式的 DoT 查詢內容，兩者都拿不到。

## 6. 逐 App DNS 過濾的可行性

分兩件事，結論不同：

- **把「系統解析器」的查詢歸屬到某個 App → 不可行（分類 D）。** 唯一的公開 uid 歸屬 API 是 `ConnectivityManager.getConnectionOwnerUid(protocol, local, remote)`（**API 29+**，僅 TCP/UDP），它回傳 socket 擁有者；裝置的 DNS 是**系統解析器**送出的，所以 tunnel 只會看到解析器。查不到時回 `Process.INVALID_UID`，非該使用者的作用中 VpnService 會丟 `SecurityException`。
- **但 App 自己的 DNS／DoH／DoT socket 是可歸屬的（分類 A，API 29+／部分 C）**：這種情況 socket 擁有者就是該 App，`getConnectionOwnerUid` 能給出 uid。也就是說「不可行」只適用於走系統解析器的一般查詢。
- **「這個 App 的流量要不要進 tunnel」→ 可行，且已實機驗證。**

實機驗證（`artifacts/run-20261015-perapp/`，私人 DNS `off`）：

| 步驟 | tunnel 的 `Uids` | 系統解析器探針的本機封鎖計數 |
| --- | --- | --- |
| 未排除任何 App | `0-99999, 9500000-9599999` | **+1** |
| 排除 `tw.kuies.block` | `0-10669, 10671-20669, 20671-99999`（10670、20670 消失） | **0** |
| 改排除 `com.adguard.android` | 只有 10665、20665 消失 | （未量測其解析） |

- 排除是**逐 uid、專一、可逆**（清除後 10670 回到集合內）。粒度是 UID 不是套件（NetGuard FAQ 也是同一句：Android 以 UID 分組）。
- 官方javadoc的語意：被排除的 App「will use networking as if the VPN wasn't running」；`addAllowedApplication` 則相反，一旦使用它，**未列出的 App 全部不受保護**；兩者**不能混用**（`UnsupportedOperationException`），清單只限**呼叫中的使用者**已安裝的套件，且同時只能有一個 active VPN。
- 因此語意只能是「**該 App 完全不進 tunnel ＝ 完全不受本機規則保護**」，不是「該 App 用不同規則」，也不是「只排除它的 DNS」——後者不是平台概念。
- **證據等級**：行為面只能由 KuiesBlock 自己的 package 驅動（唯一能發查詢又能觀測的 App）；第三方 App 只驗證到 uid 層級。
- strict 模式下逐 App 開關**沒有意義**（本來就沒有系統查詢進 tunnel）。

## 8. 未來規則匹配的明確插入點，以及一次查詢的事件順序

- **插入點**：`KuiesVpnService.handleQuery`（`KuiesVpnService.kt:685`），本機規則在 `:689` 查詢 → `localBlockReply`（`:735-745`）→ `FilterSnapshotHolder.snapshot()` → `LocalDnsFilterPolicy.blockReply`（`vpn/LocalDnsFilterPolicy.kt:32-42`，命中即 NXDOMAIN）。
- **在那裡拿得到的資訊**：`TunnelDnsQuery`（`DnsTunnelPacket.kt:16-25`）＝transactionId、clientAddress、clientPort、queryBytes/queryLength、ednsUdpPayloadSize、domain，加上 `routePlan.mtu`。
  **拿不到的**：uid、package、來源介面、TTL。client IP/port 是短命的，且會被多個 App 共用，**不能當 App 身分**。
- **順序**：讀取 → 解析（不符就丟、不回覆）→ `dispatch`（`:670`）**先記錄查詢統計**（`:671`）再排隊（佇列滿＝`recordFailure` 且查詢被丟、不回答）→ `handleQuery`：**先本機規則**，命中就 `recordBlock()` → 回 NXDOMAIN → **直接 return，不發 DoH** → 否則才走 DoH（null transport／Failure → SERVFAIL）。
- **fail-open**（`:879`）：設為 `ERROR`、發停止通知、`stopSelf()`，讓系統解析器接手。觸發條件包含啟動 watchdog 15 秒、沒有底層網路、非 DoH 端點、路由計畫不安全、沒有安全宣告、E1 沒有解析位址、`establish()` 失敗、探測耗盡，以及 **連續 5 次 DoH 失敗**。**fail-closed** 只發生在單一查詢層級（默默丟棄、截斷、SERVFAIL、佇列滿），tunnel 本身都還活著。
- **成本結構**：1 個 reader 執行緒＋8 個 worker（`ArrayBlockingQueue(256)`、佇列滿即丟）＋每次回覆一次 `writeLock` 同步的 `FileOutputStream.write`；每次 DoH 一次 OkHttp 呼叫（共用 `ConnectionPool(2, 5min)`、callTimeout 8s），本機命中不發 HTTP。

## 9. 三種架構比較

| 指標 | A. 維持 DNS-only + E2 共存 | B. 在 DNS-only 上擴充 DNS 能力 | C. 更完整的本機 VPN／網路堆疊 |
| --- | --- | --- | --- |
| 本機規則能真正套用 | `off`／AUTO：可以；strict：不行 | 同 A | 同 A（strict 仍只能做到位元轉送，看不到內容） |
| strict 私人 DNS 相容 | 已共存（E2），且誠實顯示不攔截 | 同 A | 若把 DoT IP 導進 tunnel 需自製 TCP 狀態機＋憑證信任問題，實質不比 A 好 |
| 逐 App 過濾 | 可（語意＝不進 tunnel） | 同 A | 同 A（沒有更多；仍無法逐查詢歸屬） |
| Per-query App 歸屬 | 不可（系統解析器） | 不可 | 不可（除非該 App 用自己的 DNS socket） |
| 使用者需額外設定 | 無；strict 下需知道本機規則不生效（可選改 AUTO） | 無 | 需處理相容性與潛在斷網 |
| 開發複雜度 | 低 | 中（TCP/53、IPv6 解析） | 極高（tun2socks 級；原生程式庫被排除） |
| CPU／記憶體／電量 | 最低（現況） | 略增 | 顯著增加（長連線狀態＋重傳計時器） |
| 對 v0.3.0 網路穩定性的風險 | 無（不變） | 中（DNS 逾時拖慢全機解析） | 高（TCP bug 直接斷全機 DNS） |
| 未來維護成本 | 低 | 中高 | 高 |

**推薦：A（維持 DNS-only + E2 共存），並把 B 限縮為「只做真的買得到的東西」。**

理由：C 增加大量複雜度卻**換不到 strict 模式的過濾能力**（TLS 端到端，轉送也只轉位元），直接違背「輕量、簡單、免費、不誤擋」的定位。B 裡唯一有價值的擴充是 `off`／AUTO 模式下更完整的解析相容性（例如 TCP/53 截斷重試），可以在真有需求時再做。真正的使用者價值在過濾規則本身，而那在 A 的架構下就完全做得到。

## 13. TCP/53 靜默丟棄與過大 DNS 回覆：改善評估

**現況（已在程式碼驗證）：**

- TCP/53 送往 `10.111.222.2` 由 `DnsTunnelPacketParser.parse` 判為 `NOT_UDP` → 只記一次 log，**不回任何封包**（`DnsTunnelPacket.kt:46-48`；`KuiesVpnService.kt:616-627`）。
- 上游回覆超過 UDP 預算時走 `DnsMessageWriter.truncated` → header-only、rcode NOERROR、**TC=1**（`DnsMessage.kt:289-290`，TC 位元在 `:270` 設為 `0x0200`）。
- **兩者串起來才是真問題**：TC=1 是在告訴解析器「改用 TCP 重問」，而那個 TCP 查詢正是被靜默丟棄的那一種 → 解析器只能等自己的逾時後失敗，而不是快速失敗。
- 發生機率不高：客戶端沒帶 EDNS OPT 時預算直接放寬到 `mtu-28`（1472 bytes），所以只有大於 1472 bytes 的回覆才會截斷。

**評估：小型修正可行，且不需要 TCP 狀態機。**

- **建議修正（小）**：對「送往虛擬 DNS 的 TCP 封包」回一個**無狀態 TCP RST**（依 RFC 793：帶 ACK 的區段回 `seq=ack, RST`；只帶 SYN 的回 `seq=0, ack=seq+1, RST+ACK`）。因為我們是**無條件拒絕**而非代理，所以不需要連線狀態、不需要重傳計時器。
  需要新增：TCP 標頭解析（ports/seq/ack/flags/data offset）＋RST 區段建構（含 pseudo-header checksum，可重用既有 `Checksums`）＋IPv4 標頭（既有 `Ipv4Parser.buildHeader`）。估計含測試約 150–250 行，屬既有封包層的自然延伸。
  效果：解析器立刻得到「連線被拒」並快速失敗或改用其他伺服器，不再空等逾時。
- **建議修正（小，可選）**：為「截斷」與「TCP 丟棄」各加一個**計數器**（不含任何查詢內容），讓實際發生頻率可被觀測，再決定要不要投入。
- **不建議**：實作完整 TCP/53 DNS 代理（＝使用者空間 TCP 狀態機，1.3k–2k 行、常駐連線狀態與重傳計時器），與「輕量」定位不符，應留待真有需求時另立里程碑。

**插入點確認（第 8 節的前提）**：`localBlockReply` 在 `snapshot.isEmpty` 時直接回 null（`KuiesVpnService.kt:735-745`、`LocalDnsFilterPolicy.kt:33`），本機命中的回覆走**同一支** `writeBack`／`UdpDnsReplyWriter.buildReply`（`:746-762`），NXDOMAIN 為 header-only、`truncated=false`，遠小於預算（`LocalDnsFilterPolicy.kt:40-46` 若塞不下就回 null 交還上游）。因此插入本機規則**不會改變** DoH 路徑與封包形狀；沒有任何規則時（`snapshot.isEmpty`）行為與加入此功能前逐位元相同。

## 14. 尚存風險與需要進一步驗證的項目

1. **AUTO 模式的不確定性**：本次量測有攔到，但 opportunistic 的 DoT 升級不受我們控制，廠商 ROM 也可能有不同路由。UI 說明需與實際觀測一致。
2. **上游層級無法覆蓋**：本機允許規則永遠擋不住 AdGuard Home 端的封鎖，產品說明要寫清楚（已納入第 12 節）。
3. **TCP/53 RST 修正尚需真機驗證**：範圍小，但一旦上線就必須用真機確認「截斷後的重試確實快速失敗，且不影響正常查詢」。
4. **未完成／未驗證的項目**（誠實列出）：逐 App 實驗中「清除排除後行為恢復為 +1」那條沒量到（只有 uid 集合恢復可見）；未做端到端 CPU／電量 profile；`::/0 unreachable` 對 IPv6-only App 的實際影響未量測；AdGuard 是否另有文獻使用「network compatibility」一詞未找到（UNVERIFIED）；Blokada 官方文件兩個 URL 皆 404，因此本報告不做任何 Blokada 陳述。

## 15. strict DoT 撥號的目的地與 tunnel 內的 IPv6 封包（2026-10-16 直接取證）

以 worktree 診斷建置（**只**把 `LOG_DROP_ENDPOINTS` 設為 true，路由／DNS／TLS／E2／過濾引擎完全未動）
跑一次 `device-test.ps1 -Scenario dns-declaration -AllowDeviceChanges -StopOtherVpn`（12/12 PASS），
artifacts `artifacts/run-20261016-133127-dns-declaration/`。以下為**直接觀測**，不是路由推論。

**TCP 853（BASELINE + strict）：**

```
tunnelDrop ipv4 proto=6 dstPort=853 src=10.111.222.1 dst=10.111.222.2 flags=SYN reason=NOT_UDP
```

- 來源 `10.111.222.1`＝tunnel 介面位址（系統解析器在 VPN 網路內的 socket）；目的 **`10.111.222.2`**＝
  我們宣告的虛擬 DNS；目的埠 853；**TCP flags = SYN**。
- 次數：baseline 相位 7 個 drop、其中 **1 個是 853**；E1、E2 各 **0** 個。上一輪的單一路由推論
  **已由直接觀測證實**。
- 意義：**strict 模式的 DoT 撥號確實送到本機 tunnel 內的位址並被丟棄**（`NOT_UDP`，握手從未開始，
  tunnel 因此未通過驗證）。這是「憑證終結」路線在結構上成立的唯一理由——阻礙只剩 TLS 身分。

**IPv6（所有被觀測到的形式）：**

```
tunnelDrop ipv6 nextHeader=0  src=fe80:…:a40e dst=ff02::16 reason=NOT_IPV4
tunnelDrop ipv6 nextHeader=0  src=fe80:…:a951 dst=ff02::16 reason=NOT_IPV4
tunnelDrop ipv6 nextHeader=0  src=fe80:…:6625 dst=ff02::16 reason=NOT_IPV4
tunnelDrop ipv6 nextHeader=58 src=fe80:…:a40e dst=ff02::2  reason=NOT_IPV4
tunnelDrop ipv6 nextHeader=58 src=fe80:…:a951 dst=ff02::2  reason=NOT_IPV4
tunnelDrop ipv6 nextHeader=58 src=fe80:…:6625 dst=ff02::2  reason=NOT_IPV4
```

- 來源全部是 **`fe80::/10` link-local**（三個不同位址對應三次 tunnel 世代）；目的分別是
  **`ff02::16`（all-MLDv2 routers，Multicast Listener Discovery v2）** 與 **`ff02::2`（all-routers，
  ICMPv6 Router Solicitation）**。
- 判定：這是**核心為 tun 介面自己產生的 IPv6 連結本機控制流量**（MLDv2 listener report 與 Router
  Solicitation），**不是使用者流量**。先前的假設現已由位址直接證實。
- **尚未確認**：drop 記錄器會去重且有上限（`MAX_LOGGED_DROP_DETAILS`），所以「只出現這幾種形式」
  不等於「沒有其他 IPv6 封包進入 tunnel」——使用者 IPv6 流量是否也會進入，**仍未確認**。
- **對使用者的影響仍未量測**：這些是 link-scope 控制封包，被丟棄不影響使用者的網際網路連線；但
  `VpnRoutePlan` 的註解「IPv6 完全留在底層網路」在**介面控制流量**這一項與實測不符，應修正註解
  而不是把日誌消掉。

**已確認**：strict 的 DoT 撥號在「有宣告 DNS」時確實進入本機 tunnel 且帶 SYN；strict 只認
`privateDnsCfg.ips`、無明文 fallback；驗證走系統信任庫並比對設定主機名稱。
**尚未確認**：使用者 IPv6 流量是否也進入 tunnel；`PrivateDnsBroken`（情境 logcat 僅含 App tag，
需 system network tags）。

**對 v0.4.0 的影響**：不改變方案 A，也不改變第一里程碑。要能在本機完成 strict 的 TLS 握手，必須持有
**該釘選主機名稱的系統受信任憑證與私鑰**——只有自有 DNS 主機可行，**任意第三方私人 DNS 主機不可能**；
且正式 DNS 服務的 TLS 私鑰**絕不可打包進公開 APK**。因此 **DoT 終結不列入 v0.4.0，本支線到此收束**；
除非出現「直接影響使用者正常上網」的新證據，不再追加研究。
